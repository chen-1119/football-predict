## 本系统应该落地什么

| 方向 | 对标实施 | 验收标准 |
| --- | --- | --- |
| 精选推荐 | 保留全赛程参考，在其中建立赛前确定的精选集合；用历史覆盖、校准可靠性、报价时效与模型稳定性筛选 | 每场有入选或观望原因；赛后不能修改精选集合；同时报告覆盖率 |
| 玩法选择 | 从同一比分概率矩阵比较普通胜平负、整数让球，再输出主推玩法、方向、概率和 SP | 赛程、推荐、详情和串关同一 decisionId；普通平局不能脱离让球符号机械转换 |
| 双选 | 增加独立的双选研究分组；概率按比分事件并集计算，重叠结果只计一次 | 单选/双选胜率分开；收益使用实际分配资金；不把两项选择当成单项成本 |
| 历史复盘 | 首页给近 7/30 日摘要，详情按竞彩日、玩法、单/双选、版本筛选 | 展示有效样本、待结算、缺赔率、覆盖率、净收益和区间；来源证据等级分组 |
| 推荐解释 | 固定输出支持证据、反向风险、为何选择该玩法三部分 | 每条事实可追溯到真实输入；无 Elo/近期样本时不能生成虚构球队分析 |
| 交互 | 浅色卡片、首屏短结论、详情展开数据；独立展示未发布/观望/待结算/已结算 | 用户能完成查看内容→登录→关注→复盘；数据空缺不是无限加载 |
| 多模型 | 现有市场、Elo、近期/Poisson分别显示贡献；语言模型只整理证据与分歧 | 不因多个模型同意就抬高未经校准的概率；不让文案改变已冻结推荐 |

## 玩法联动示例

假设同一模型给出主胜 40%、平局 33%、客胜 27%，且官方整数让球是主队 -1。普通胜平负最大项仍是主胜 40%；“让负”对应普通平局或客胜，合计 60%。两个玩法不应只按文字一致强行选主胜/让胜，需要根据完整比分分布及对应 SP 比较。概率较高仍不等于收益较好，必须检验价格与校准。

主队 +1 时关系不同；“普通平局必选让负”不成立。比分候选从同一矩阵给出。双选若跨玩法，先计算事件并集，不能直接把两项概率相加。

## 执行顺序与证据边界

1. 本轮优先修复球队映射、历史采集和 PostgreSQL 到 Elo/form 的真实输入；补充缺赛果。
2. 下一版本做精选集合、主推玩法和复盘分组展示；沿用已有账号/关注功能。
3. 双选及权重/平局校准作为独立研究分组，按比赛日滚动验证后再决定是否发布；不给人造高胜率目标。
4. 最后完善会员权益。会员内容以更完整的解释、筛选、跟踪和复盘为核心，不能把参考状态包装为已验证稳定收益。

本报告提出产品方案，未实施对标 UI、双选策略或付费功能。当前代码修复与该方案分开验收。
