# 基础链路修复：2026-09-11

本次只处理数据读取、写入、历史保护和发布准入，不修改推荐模型、命中率口径或新增 UI。

## 已定位的根因

线上 mutable `prediction-snapshots.json` 为 536,933,381 字节，超过 Node 单字符串上限。完整 JSON 实际有效；此前整文件 `Buffer.toString/JSON.parse` 把运行时容量异常报告成了 JSON 损坏。同步加载器还有“读取失败返回空历史”的风险。

另一问题是发布准入把新一轮重试的 `ok:true, phase:official-result` 当作可继续准备，即使 `lastCycle` 仍是失败，导致不同检查时刻可能得到不同准入结果。

12:07 日志进一步确认当前同步的直接错误为 `PUBLIC_REFERENCE_EVIDENCE_BINDING_MISSING`。12:09 对同一 SHA 原始快照的只读验证发现 198 条记录与 198 条证据全部绑定有效；把证据数组模拟为空可复现完全相同的错误。因此本次不补造证据，而是修复吞掉读取错误的加载路径。证据 `outputs/foundation-binding-proof-1789099778848.json`，耗时 15,242 ms、峰值 215,704 KiB、生产写入 0。

## 已实施的代码修改

1. 新增分块 JSON 读取器：64 KiB 读取缓冲，完整保留对象及所有数组，不构造整文件字符串。校验 UTF-8、语法、文件稳定性、摘要和大小；内存仍包含完整对象图，不宣称常量内存。默认文件准入 2 GiB、单标量 16 Mi 字符、深度 256，越界明确拒绝。
2. 接入 mutable generation、immutable generation、大快照同步、归档迁移、SQLite 导出输入、策略/能力检查和相关发布验证器。immutable generation 小于 32 MiB 的请求缓存路径保留原生解析速度；大投影走分块读取。
3. 快照写入改为紧凑 JSON，并逐条写所有顶层数组，包括 observations 和公开推荐证据；临时文件 fsync、原子替换、分块相等比较仍保留。只改物理格式，不改对象字段、方向、SP 或历史保留策略。
4. 已存在快照的读取错误、rows 或公开证据类型错误直接阻止同步，不能再作为空历史继续写入。
5. 只有时间顺序正确的新官方发布证据，才能解除上一轮官方失败的准备阻断；“重试运行中”不能解除。
6. 在线构建入口在时间窗口、归档观测、验证链、序号预留和打包前先检查 worker。失败时不上传、不开始构建。上传前和服务端最终检查均保留；没有任何跳过验收开关。
7. 将新读取器纳入签名包必需文件，并更新验证复用的依赖闭包：代码、依赖或运行时改变后旧回执失效，不能直接套用旧成功结论。

## 明确未完成

本次代码修复不等于上线，也不等于 SQLite 已退役。线上仍需受控修复发布及真实 worker 完整官方周期验收。正常发布流程目前要求旧 worker 在切换前成功发布，而旧 worker 正被同一个大文件问题卡住；单独放开早期门槛、重打包、临时压缩一次文件，都不能解决这个顺序依赖。

后续修复发布必须绑定签名代码和当前运行版本、保护原始文件和冻结推荐、隔离运行新代码、具备明确恢复记录，再验证新 worker 发布及数据库/数据版本一致性。不能伪造旧 worker 成功、绕过完整性门槛或用失败的 r723/r724/r725 包当已验收基线。此受控切换路径尚未实施，本次不创建新的发布包、不重复上传。

PostgreSQL-only 切换、停用兼容 SQLite 发布步骤，以及失败包清理仍属后续工作。没有删除用户数据库、备份或原始工作区。
