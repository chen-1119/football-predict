# 原生发布的连接隔离与真实恢复验证

最终数据镜像完成后，如果仍允许新连接进入旧库，就存在新写入落在镜像与数据库改名之间的间隙。因此增加 `fenceNativeDatabaseConnections`：先核对集群、旧库和候选库 OID、所有者及归档库不存在，再事务性关闭两个库的新连接。已有发布器连接可完成最后的数据同步和核对；其他连接必须排空，生成指针写入屏障仍须保持。函数不终止连接、不改写业务数据、不改名数据库。

连接隔离必须在 v4 恢复日志持久化之后使用。恢复器读取真实集群和 OID 判定切换状态，在启动应用前重新开放身份匹配的 `football` 库；归档库保持关闭。这样在数据库改名前断电也能恢复旧服务，改名后恢复兼容应用也不会倒退新数据。不能把未提交的 `ALLOW_CONNECTIONS=false` 当成已生效的连接隔离。

数据库锁行为核对依据：[PostgreSQL 16 官方源码](https://github.com/postgres/postgres/blob/REL_16_STABLE/src/backend/commands/dbcommands.c)，并以本地 PostgreSQL 16.15 实际连接拒绝及恢复测试验证。

`scripts/verifyNativeRecoveryDatabase.cjs` 使用全新、随机端口的 Windows PostgreSQL 集群。它执行真实数据库改名、真实恢复 CLI 文件操作及原始恢复器的数据库查询，仅将 Linux psql 路径重定向到该临时集群；systemd 和 HTTP 仍为测试替身。验证五种场景：

- 日志已准备、两个库已关闭新连接、尚未改名：恢复原应用并重新开放旧库。
- 数据库已改名、应用尚未交换：根据实际 OID 恢复兼容应用和原生配置。
- 应用已交换后回滚：数据库中的新赛果、模型账本及生成指针均保留。
- 事务已提交后的前滚恢复：新应用和原生数据保持生效。
- 已处于原生模式的应用版本回滚：数据库身份和新增数据保持不变。

补充测试明确验证：新连接被拒绝，隔离前已有的发布器连接仍可读取；恢复重新开放正确的活动库，候选／归档库不被误开放。证据为 `outputs/native-recovery-fence-result.json`，五项通过、临时集群已关闭清理。原有 v4 恢复拒绝场景也全部通过，证据为 `outputs/native-recovery-fence-fixtures.json`。

数据库镜像的状态写入改为固定 SQL 加数组参数，减少大批次 SQL 解析开销；首次镜像已证明状态表为空时使用普通插入，已有镜像记录或需要重建校验基线时仍使用冲突更新。逐行 HMAC、原始内容哈希、事务编号检查、600 秒上限、候选库隔离和篡改拒绝标准均保留。`outputs/native-mirror-array-regression-result.json` 的真实 PostgreSQL 回归通过，SQLite 访问为 0。真实数据量的性能验收仍须单独完成。

本提交仍不是生产切换验收：必须先接受完整兼容运行包，然后完成签名发布器接线、候选库／生成文件绑定、写者排空、完整备份恢复证明、全量投影比较和一次真实原生 Worker 周期。`BOOTSTRAP_SHA` 在尚未接受兼容整包时继续保持为空。
