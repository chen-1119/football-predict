# 发布磁盘容量恢复（2026-10-07）

## 已确认原因

r801 在候选构建的 generation reconciliation 阶段复制文件时收到 `ENOSPC`，在应用切换前失败。正常恢复结束，运行和完成标记仍为 r793。磁盘块空间不足；inode 使用率约 3%，不是 inode 耗尽。本机 C 盘仍有约 62 GiB 可用空间，本次故障发生在服务器根文件系统。

现场读数表明 PostgreSQL 目录约 80.64 GB，发布材料目录约 52.97 GB。其中累积了多个旧发布的临时候选数据库。另发现 `native_exit` 在固定恢复程序成功后没有调用既有 `cleanup_build_tree`，这次失败留下约 2.81 GB 的候选构建副本。

## 已执行清理

北京时间 2026-10-07 00:48 完成：

- 删除独立核验、无进程和挂载引用的 r801 失败构建目录，约 2.81 GB。
- 分两次正常 `DROP DATABASE` 删除 r773、r776、r779、r780 四个已完成发布的临时候选库，目录逻辑大小合计约 25.21 GB。
- 每次取得新的同集群名称/OID、owner、零连接、正常 complete/final、runtime-only 双生产 OID/空 cutover 合同证据，验证原 dump 字节与签名原始归档，持正常发布锁执行；每个删除单独留存回执。
- 服务器可用空间实际读数为 **29,087,547,392 bytes（约 29.09 GB）**。各目录大小与可用空间变化采用不同统计口径，后台写入及 PostgreSQL 自身空间管理也会改变余量。

生产库、legacy 库、当前 r793 和失败 r801 的 native 材料、原 dump/seed、签名归档、恢复材料均保留。运行和完成标记保持 r793；网站与采集服务 MainPID、active/running 状态在清理前后保持一致。

00:50 的新生产 PG 只读核对确认：基线 44,513 个 `decisionId/recordHash` 全部保留，缺失和变化均为 0；四份已封存原件字节不变。这是上述身份与哈希的连续性核验，不是全业务 payload 重新计算。

## 源码修复

`native_exit` 的失败处理顺序为：停止候选服务、心跳和写入屏障 → 固定恢复程序成功 → 确认构建用户没有进程 → 既有带路径限制的构建目录清理 → 记录失败并保留非零退出码。任何停止、恢复或构建用户静止检查失败时保留构建副本。

新增 `verifyNativeReleaseFailureCleanup.cjs`，在独占临时目录执行真实 Bash 函数：覆盖恢复成功清理、各种停止/恢复/静止/删除失败、意外路径拒绝和原退出码，并核对正常成功路径的清理顺序。测试注册到必需签名前验证与归档清单。

此文记录现场清理和源码修复范围。新的源码发布仍需要固定提交、全新构建及签名归档、真实发布窗口、完整验收；r801 失败归档和序号保留，不以同一失败归档重试。
