原目录上限为 256 MiB / 512 批。已保存的一批真实 Linux 新计算（34 条记录）压缩后 767,824 字节；若每五分钟保存同样大小的一批，原字节上限约 349 批、29.1 小时就先耗尽，不能只看文件数上限对应的 42.7 小时。这是样本大小外推，不是生产已经连续运行这么久的观测。

本次保持原内容寻址 `.json.gz` 文件格式、原始内容哈希、完整输入输出、每记录/每批大小上限和独占锁，修改存储预算与可观测性：

- 目录最大 **48 GiB / 60,000 批**，不预分配磁盘、不创建付费资源；旧文件原位保留，不迁移、重压缩、覆盖或自动删除。
- 每次新写入前读取实际文件系统可用空间，检查写后仍有 **8 GiB 余量**；无法取得可靠空间信息或预算不足则停止新增，保留原模型计算返回值和旧批次。
- 这是写前观察保护，不是独占磁盘预留；其他服务仍可能同时用盘。真正 ENOSPC/写入失败继续返回错误，不冒充成功，不删旧证据释放空间。
- 返回实际文件数/压缩字节、上限、当前批次大小和剩余可容纳批数；按“同样压缩大小、每五分钟一批”估算剩余天数，少于 30 天标 watch，耗尽标 full。估算明确不是保留时长保证。
- 相同已保存批次先验证内容，再按 duplicate 返回；即使此刻空间不足或无法读取剩余空间，也不把已经验证留存的文件说成未保存，但容量状态不能是健康。

沿用平面目录，仍在同一独占锁中逐文件核算，拒绝未知文件/链接/异常容量；没有用一份可能失真的累计计数替代实际磁盘文件清单。60,000 文件量级的核算开销另做了真实 Linux 测量，见下文。

以那一批 767,824 字节为假设，180 天、每五分钟一批约需 51,840 个文件、37.1 GiB；新文件上限约对应 208.3 天。实际批次变大、频率提高、其他服务用盘都会缩短时间，因此不能承诺“已经解决所有六窗留存”或“保证 208 天”。
