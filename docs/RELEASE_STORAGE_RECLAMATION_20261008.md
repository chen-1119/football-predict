# 发布存储回收补充（2026-10-08）

## 原因与当前状态

用户要求定时清理旧发布候选数据库和发布事务材料。旧日志/每日备份保留策略未覆盖这两类；每次完整发布留下约 6GB 以上的候选数据库，构建目录清理不能回收这些库。失败事务还可能保留未完成的候选库、dump 和 generation 副本。

当前代码阶段：容量检查已接入候选数据库分配前；回收候选判定为纯函数，尚无删除执行器、系统 timer 安装或线上释放空间。不能把此文档或 dry-run 当作定时清理已上线。

## 第一阶段执行策略

计划每日北京时间 05:10 检查，每次最多处理两个发布；与发布共用正常 fd9 锁，遇发布或恢复事务跳过，不能终止连接或强制抢锁。

| 对象 | 进入候选的条件 | 执行时仍需证明 |
| --- | --- | --- |
| 旧发布候选库 | runtime-only、完整发布成功超过24小时；保留当前运行、当前回滚及最近两个成功版本 | 精确集群/name/OID/owner、0连接、无外部引用、保留 dump 和原签名包验签、访问角色已退役 |
| 旧事务 seed/refresh store | 同上，仅明确列出的 `seed-<整数>-store` / `refresh-<整数>-store` | 目录真实路径/文件树/无挂载及进程引用；不再被运行或恢复使用；删除后记录墓碑 |
| 失败、未完成、身份未知的事务 | 不因年龄自动删除 | 独立核实回滚完成、依赖释放后再扩展规则 |
| dump、签名包、journal、状态及回收回执 | 第一阶段保留 | 后续单独制定恢复材料保留周期，不能与重复 store 一并递归删除 |

“64GB候选库”和“36.7GB事务材料”是盘点范围，不是可全部释放的空间。不能用 `mtime`、名称前缀或零连接中的任一项单独决定 DROP。

## 容量检查

`nativeReleaseCapacity.cjs` 实际读取生产数据库大小、当前 generation 与应用目录大小，按文件系统设备合并候选复制、mirror/WAL、dump、构建与保留空间需求。使用 `bavail`，禁止把其他磁盘的空闲量借来通过检查。外部 tablespace、未知容量、数值溢出均拒绝。

检查在 native allocate 的目录和 CREATE DATABASE 之前执行；失败不创建该候选库。它不是空间预留，不能保证之后没有其他写入，也不替代原发布窗口、服务和恢复检查。保守预算系数尚须用真实部署峰值继续验证。
